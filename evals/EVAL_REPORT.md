# AI grading-accuracy eval report

This documents the first real run of the [`/evals`](README.md) harness: building
a hand-rated dataset, measuring how well the AI coach's scores agreed with a
human rater's judgment, diagnosing the biggest source of disagreement, fixing
it in the prompt, and re-measuring. This is the artifact referenced by
[README.md — Known limitations](../README.md#-known-limitations--roadmap)
("grading calibration is in progress").

- **Model:** `gemini-2.5-flash-lite` (production; Runs 1-2), then
  `gemini-3.5-flash-lite` (eval-only default; Runs 3-4, after the production
  model's free-tier quota was exhausted — see Run 3 below)
- **Dataset:** [`dataset.json`](dataset.json) — 17 hand-written question/answer
  samples across 6 common interview questions (debugging, disagreement,
  prioritization, a proud project, receiving feedback, learning new tech),
  spanning clearly weak, clearly strong, and deliberately middling answers.
- **Ratings:** all 17 `human_score` values (0-100 scale) were entered
  manually via `rate.py` by the project owner, grading the way an
  interviewer would on relevance, specificity, and structure.
- **Method:** `run_eval.py` wraps each sample in the same `AnalyzeInput`
  shape the real `/api/analyze` endpoint sends, and calls the production
  `CoachService().coach(...)` path directly — no mocking, no shortcuts.

## Timeline

1. Seeded 12 samples deliberately at the extremes (weak vs. strong) to sanity-check the harness end-to-end.
2. Ran the eval once with 2 samples as a smoke test against the real API — confirmed the pipeline worked (weak answer scored 25, strong answer scored 95).
3. Added 5 more samples in the *middle* of the scale (real examples, but missing quantified results — "it seemed to help," "people liked it," no hard metrics) once the extremes-only set stopped being informative.
4. Rated all 17 samples by hand.
5. Ran the full baseline eval.
6. Diagnosed a systematic miscalibration on the middle-tier samples (see below), tightened the coach prompt, and re-ran.

## Run 1 — baseline

Full results: [`results/20260918T094623Z_baseline.json`](results/20260918T094623Z_baseline.json)

| Metric | Value |
|---|---|
| Samples graded | 17 / 17 (0% parse failures) |
| Mean absolute error | **12.353** |
| Pearson correlation | 0.964 |
| Within 10 points | 58.8% |
| Avg latency | 1.56s |

The AI *ranked* answers almost exactly the way the human rater did (correlation
0.964), and the clearly-weak/clearly-strong samples (`s01`-`s12`) were all
within 5-15 points. But every one of the 5 new **middle-tier** samples —
answers with a real example but no quantified or clearly resolved result —
was scored **15-30 points higher** than the human rating:

| Sample | Human | AI | Gap | Answer summary |
|---|---|---|---|---|
| s13 | 65 | 65 | 0 | Debug story, no tools/metrics/timeline |
| s14 | 55 | 75 | +20 | Disagreement resolved, but outcome ("did seem to help") unquantified |
| s15 | 60 | 75 | +15 | Real prioritization example, vague result |
| s16 | 40 | 65 | +25 | One real project, adoption described softly, no numbers |
| s17 | 45 | 75 | +30 | Believable tech ramp-up, no concrete deliverable |

**Root cause hypothesis:** the coach's system prompt (`backend/services/coach.py`)
told the model to grade on "relevance, specificity and structure" but gave no
numeric anchor for what a *plausible-but-unevidenced* answer should score. The
per-interview rubric text (generated by `PlannerService`) usually includes
score bands (Excellent 80-100 / Average 50-70 / Weak 0-50), but the coach's
own fixed instructions didn't reinforce that a fluent, structured answer
without a verifiable result should be capped in the 40-65 range rather than
defaulting toward "sounds good, mark it high."

## Prompt change

Added explicit calibration anchors to `SYSTEM` in
[`backend/services/coach.py`](../backend/services/coach.py), independent of
whatever rubric text a given interview supplies:

```python
Calibrate scores against these anchors, regardless of how the supplied rubric phrases them:
- 80-100: a specific real example with a clear situation/action, AND a quantified or otherwise
  verifiable result (a metric, a concrete deliverable, a named outcome).
- 40-65: relevant and structured with a real example, but missing a quantified/verifiable result,
  OR the outcome is described only vaguely (e.g. "it worked out", "people seemed to like it").
  A plausible-sounding answer with no hard evidence of impact belongs here, not above it.
- 0-35: generic, off-topic, or no concrete example at all, even if fluent or confident in tone.
Do not default to a high score just because an answer sounds fluent or plausible; the deciding
factor is whether the result is evidenced, not how the answer is phrased.
```

`backend/tests` (24 tests, all mocked) were re-run and still pass — this is a
prompt-only change with no effect on validation, evidence-checking, or
aggregation logic.

## Infrastructure fix found along the way

The first full run (17 samples, no delay between calls) failed on 10 of 17
samples with a generic `"The AI service is unavailable"` error. Direct
reproduction against the Gemini client revealed the real cause:

```
429 RESOURCE_EXHAUSTED: Quota exceeded for metric
generativelanguage.googleapis.com/generate_requests_per_model,
limit: 5, model: gemini-2.5-flash-lite
```

The API key is on Gemini's free tier, capped at 5 requests/minute for this
model. `backend/gemini.py` intentionally collapses every failure mode (bad
JSON, incomplete grades, network errors, rate limits) into one generic
`GeminiInvocationError` for the production app (so end users get one
sensible retry message instead of a leaked stack trace) — which meant
`run_eval.py` couldn't originally tell a real failure apart from a rate
limit. Fixed by adding pacing and retry-with-backoff to the eval runner
only (`--delay 13`, `--retries 2`, `--retry-delay 20` by default) —
production behavior and `backend/gemini.py` were not changed.

## Run 3 — a second calibration pass, and a model switch

After Run 2, sorting samples by remaining error showed two clean systematic
patterns instead of noise:

| Pattern | Samples | Direction |
|---|---|---|
| All clearly-weak answers (human score 5-20) | `s01, s04, s06, s08, s10, s12` | AI consistently **10-15 points too high** |
| All human-100 answers | `s02, s07, s11` | AI consistently **5-15 points too low** |

This pointed at the Run 2 anchors themselves: the bottom band (0-35) was too
wide to pull truly generic/no-example answers down to single digits, and the
top band's "needs a quantified/verifiable result" language had made the
model *too* strict about requiring a literal number, penalizing answers that
clearly stated a shipped/adopted/resolved outcome without a metric.

**Prompt change (Run 3):** replaced the 3-band anchor set with 4 bands in
`coach.py`'s `SYSTEM`:
- `85-100`: real example + a clearly stated **verifiable** result — broadened
  to explicitly count "shipped/resolved/adopted" language as verifiable, not
  just literal metrics.
- `40-65`: real example, but the outcome is vague/subjective only.
- `21-39`: *new* — has at least one concrete specific (a named tool/action)
  but is otherwise thin; a small step above pure filler.
- `0-20`: tightened from 0-35 — reserved for truly generic, off-topic, or
  no-example answers.

### The free-tier quota ran out mid-experiment

Running Run 3 against `gemini-2.5-flash-lite` (production's model) hit a
**daily** cap, not just the per-minute one: the account dashboard showed
`RPD: 53/50` for that model — the daily quota was already exhausted from
Runs 1 and 2 plus retries, and no amount of pacing/backoff in `run_eval.py`
can work around an exhausted *daily* counter. Linking billing to the project
mid-session didn't immediately clear it either (quota resets don't appear to
be instant on billing changes).

**Resolution:** since Gemini quotas are tracked per-model, `run_eval.py` was
changed to default to a **different** model, `gemini-3.5-flash-lite`, purely
for the eval harness — giving it an independent quota bucket so future eval
runs don't compete with (or get blocked by) the production app's own usage
of `gemini-2.5-flash-lite`. A `--model` flag was added to override this
(e.g. `--model gemini-2.5-flash-lite`) for whenever a direct production-model
check is needed. See [`README.md`](README.md#a-note-on-rate-limits-and-the-evals-model).

## Run 4 — closing the `s17` gap (same model, prompt-only)

Run 3's per-sample breakdown on `gemini-3.5-flash-lite` was almost entirely
tight (16 of 17 samples averaged ~7.5 MAE) except one severe outlier:

| Sample | Human | AI (Run 3) | Error |
|---|---|---|---|
| `s17` | 45 | **90** | **45** |

`s17`'s answer says: *"...within a month I was comfortable enough to be
on-call for it."* The Run 3 prompt already listed "felt comfortable with it"
as an example of a vague, non-verifiable outcome (40-65 band) — but this
model still scored it 90, apparently reading "trusted to be on-call" as an
**adopted/completed outcome** (which the same prompt explicitly allowed into
the 85-100 band without a literal metric). That specific broadening — added
in Run 3 to stop under-scoring genuinely strong answers — created a loophole
this model exploited on `s17`.

**Prompt change (Run 4):** tightened `coach.py`'s `SYSTEM` to explicitly
separate a change in the *candidate's own role/trust/confidence* from a
*verifiable result of the work itself*:

> A change in the candidate's OWN role, trust, responsibility, or confidence
> (being put on-call, given more autonomy, promoted, "felt ready") is NOT
> itself a verifiable result — it must be paired with a concrete
> deliverable/outcome from the work.

## Takeaways

1. **The harness works as designed** — every round found a real, actionable
   miscalibration that would have been invisible without a human-labeled
   comparison; correlation alone looked "good" (0.93-0.97) throughout, even
   while MAE was double-digit and one sample was off by 45 points.
2. **Three targeted, evidence-based prompt changes cut MAE from 12.4 to 7.1**
   (~43% relative) and pushed within-10-points agreement from 59% to 88%,
   each time by reading the specific samples with the largest error rather
   than guessing at prompt wording — and without regressing previously
   well-calibrated cases or breaking the existing test suite (24 backend
   tests pass unchanged throughout).
3. **Remaining gap (~7 points):** still real but now spread thinly rather
   than concentrated in one failure mode. The next iteration should (a)
   confirm the `s17`-style "own-role vs. work-outcome" fix generalizes with a
   few more samples in that shape, and (b) get a same-model reading against
   `gemini-2.5-flash-lite` once its quota clears, per the "iterate on the
   eval failures" loop described in
   [`README.md`](README.md#improving-the-prompt-using-this-loop).
